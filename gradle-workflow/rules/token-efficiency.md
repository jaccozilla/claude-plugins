# Token efficiency

- When waiting on a long-running background command (a gradle build/test, the dev server), use `run_in_background` to get one notification when it's done — never poll with repeated status-check or no-op Bash calls in a loop.
- Run every gradle build/test through `gradle-quiet-with-summary.sh <gradlew args>` (on PATH from this plugin, same args as `./gradlew`) with `run_in_background`, never raw `./gradlew`. It writes full output to `build/logs/gradle-<timestamp>.log` and prints only a short summary (result, duration, failed tasks, failing tests, compile errors, log path) when done. Never start a `Monitor` for progress: every line a monitor prints wakes you for a full call that re-reads the whole conversation, which is the largest avoidable token cost. The user follows the run in the Claude Code status line instead (this plugin's status line; it shows the latest gradle phase, finished tests and elapsed time, never reaches you, and costs no tokens), and the run's completion notification is the only wake-up you need. If the user asks what a run is doing, read `build/logs/latest.progress` or the tail of the log named in `build/logs/latest.path`; for more detail, `Grep`/`Read` (with `offset`/`limit`) the log — never `cat`/dump it whole.
- Never use `cat` (or chain multiple `cat`s in one Bash call) to read a project file — use the Read tool (with `offset`/`limit` for large files) or Grep instead. Read gives line numbers and lets you pull just the relevant slice instead of dumping the whole file into context.
- To find code, search in this order, and never reach for a later option while an earlier one is available:
  1. The IntelliJ MCP search tools (`mcp__idea__search_text`, `search_regex`, `search_symbol`, `search_file`; load them via `ToolSearch` if deferred), always with a `limit` (roughly 10–20) and a `paths` glob such as `composeApp/src/**/*.kt`. They search the IDE index (which already skips `build/` and other ignored folders) and return only file/line/column coordinates, not the matching text, so follow a hit with `Read` (`offset`/`limit`) for just the slice you need. `search_symbol` locates a class/method/field by name, `get_symbol_info` shows its declaration.
  2. The IDE tools need IntelliJ running with the project open. If they are unavailable or error out, fall back to the Grep/Glob tools (text search with `head_limit`/files-only output), which also cap their output.
  3. Only if neither is available, shell out to `grep`/`find` in Bash, and always cap it: `-m`, `| head -N`, `| cut -c1-200`, `-l` for just file names, and exclude `build/`, `node_modules/` and `.git/`. Never let an uncapped search dump long lines (e.g. `strings.xml`, seed SQL, Markdown) into context.
- When the IntelliJ MCP tools are available, prefer the other ones to answering the same question with a file read or a Gradle run (they are compact, and need IntelliJ running with the project open — otherwise fall back to Read/Gradle):
  - After editing Kotlin, run `mcp__idea__lint_files` (several files in one call) or `mcp__idea__get_file_problems` to catch unused imports, unused variables and compile errors, and `mcp__idea__build_project` with `filesToRebuild` to compile just the files you changed, before reaching for a Gradle run.
  - `mcp__idea__get_symbol_info` returns a symbol's declaration and KDoc without reading its file, and `mcp__idea__analyze_calls` (`INCOMING_CALLS` / `OUTGOING_CALLS`, small `depth`/`maxChildren`) answers "who calls this" without grepping for usages and reading each hit.
  - To read a library's source (e.g. a Material3 composable), get its jar path from `search_symbol` with `include_external=true` and read that path.
  - To rename a Kotlin symbol (class, function, property, parameter), use `mcp__idea__rename_refactoring` (`pathInProject`, exact `symbolName`, `newName`) instead of a scripted find-and-replace. It updates every reference across the project in one call. It does not touch string literals or label text, so those still need a normal edit.
  - Do not use `mcp__idea__get_project_dependencies` (about 12k tokens of file names, unfiltered) or `get_project_modules` (about 2k tokens of source-set noise).
- Do not use `mcp__idea__read_file` to read a slice of a file. This IDE version's schema has only `offset`/`limit`, and with a `limit` it reads to the end of the file and returns just `limit` lines as a head and a tail with the middle elided, not the window you asked for. The documented `mode`/`start_line`/`end_line`/`max_lines`/`indentation` parameters are ignored here and return the entire file. Use the built-in Read with `offset`/`limit` instead. Revisit this once the IDE or its MCP plugin supports the documented modes.
- When probing a tool or parameter you have not used before, point it at a small file or a tight limit first: a server that silently ignores an unknown parameter returns the whole file, and doing that on a large file several times in a row is expensive.
- Make code and doc edits with the Edit tool, using the shortest unique anchor (usually one line) for `old_string` — not a Python heredoc that repeats a whole block as the text to find and the replacement. For several independent edits, issue the Edit calls together in one message. Use `mcp__idea__rename_refactoring` for symbol renames, a short `sed -i` for one identical change across many files, and `Write` for new or fully rewritten files. Reserve Python for edits that need logic (computing a value, parsing a file, a transform). The script body stays in context for every later call, so boilerplate and duplicated blocks add up.
- Default to `offset`/`limit` on Read for any file over ~200 lines, especially recurring large files — read only the region you need.
- When issuing multiple independent Read/search calls with no dependency between them, batch them into one message instead of one-call-per-turn.
