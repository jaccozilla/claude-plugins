# Running tests and test failures

## Running tests
- Run tests through `gradle-quiet-with-summary.sh <gradlew args>` (e.g. `gradle-quiet-with-summary.sh :app:jvmTest`) with `run_in_background`, never raw `./gradlew` — see the token-efficiency rules.

## Test failures
- Tests should never fail. A failing test is a problem to be fixed, full stop — "it's a test-harness issue," "it's flaky," or "it's a pre-existing environment problem" is never a reason to leave it failing or to treat the task as done. Diagnosing a failure as harness/environment-related is a step toward fixing it (the harness, the environment, or the test itself), not a stopping point.
- After making changes, run the full relevant test suite (not just the tests that obviously touch what changed) before considering the work done, and fix every failure you find — including pre-existing ones you didn't cause. Don't scope pre-existing failures out of your work just because you didn't introduce them.
- Never report a vague count like "3 existing failures" and move on. If a failure remains after real fix attempts, name it explicitly (test class/name, what you tried, and why you're stuck), then stop and ask the user for help unblocking it — never present it as an accepted/ignorable status quo. Only if the user explicitly agrees to defer it, record it (in projects with the `track-deferred-work` skill from `spec-coverage@jaccozilla-plugins`, that skill files it under `docs/todo/test-failures/`) — never silently.
- This applies even when a failure looks unrelated to your change — don't silently classify it as out-of-scope yourself. Surface it and keep working it with the user rather than parking it.
- Do not consider a task complete, and do not report success to the user, while any test is failing.

## Test history (only in projects that apply the `test-history` Gradle plugin)

Most failures are caused by the change you just made: read the failure, look at your diff, and fix it. Don't consult the history for that. Only when you can't tell whether your current changes are responsible (the failing test looks unrelated to anything you touched, or it fails in a way your diff can't explain) use the `test-history` Gradle plugin instead of checking out `main` and rerunning the suite:

- `./gradlew -q testHistoryFailures` lists every currently failing test grouped by the state it last passed in, with a verdict: `CODE UNCHANGED since then` means the failure isn't from your edits; `CHANGED since then` lists the files that changed since.
- Follow up with `./gradlew -q testHistoryLastPass --test=<text>` (when did this test last pass?) and `./gradlew -q testHistoryDiff --test=<text> [--full]` (diff from that test's last passing state to the current code). `--test` is a substring or `*` glob of the `task|class#name` key; `--task=:e2e:jvmTest` narrows by test task. `./gradlew -q testHistoryEstimate` prints the expected count and duration per test task.
- Run these lookups as plain `./gradlew -q <task>`, not through the quiet wrapper (an exception to the token-efficiency rule): they run no tests, finish in seconds and print a few lines, and the wrapper's summary would hide that output.
- A test with no recorded pass has never been seen passing here, so the history can't clear or blame the current changes; treat that as an unknown.
- The history only tells you where to look; the failure still has to be fixed, per the rules above.

The plugin records each test case's result, duration and the exact working-tree state it ran against in `.test-history/tests.json` (gitignored, survives `./gradlew clean`). The state hash is a git tree of HEAD plus all uncommitted changes, so "the code is the same as when it passed" is an exact comparison. Every run through the wrapper also prints `test-history:` lines: the expected test count and duration before it starts and actual vs expected afterwards, plus, for each failed test, when it last passed and which files changed since.

## Compose UI tests (only in projects using `compose-test-utils` from `kmp-shared`)

These helpers (`com.jaccozilla.kmp.compose.test`) are extensions on `ComposeUiTest`, for `runComposeUiTest` tests that run on both jvm and wasmJs.

- String resources load asynchronously on wasm, so use `onNodeWithLocalizedText(...)` instead of `onNodeWithText(...)` for any text that comes from a string resource — it waits for the node to exist, then returns the usual interaction (`onNodeWithLocalizedText("Search").performClick()`; as a bare statement it doubles as `assertExists`). Keep plain `onNodeWithText` for user-entered or DB-sourced text. If a test fails on wasm but passes on jvm, this is often the cause.
- Asserting localized text is **absent** can't be made reliable by waiting — an unloaded string looks identical to an absent one, and a wait-for-absence burns the full timeout whenever it's wrong. Don't write `waitUntilAssertionPasses { onNodeWithText(localized).assertDoesNotExist() }`. Prefer, in order: (1) a `testTag`/semantic-state check (`onNodeWithTag(...).assertDoesNotExist()`); (2) wait on the positive replacement state with `onNodeWithLocalizedText(...)`; (3) wait for a same-composition localized anchor, then one immediate `assertDoesNotExist()`. Plain `assertDoesNotExist` on user-entered/data text is fine.
- Handle async loading (a fetch, `Res.readBytes`, a resource load) with the page-loaded marker, never with ad-hoc waits or sleeps. Every screen that loads something asynchronously emits `PageLoaded("<page-id>")` (`com.jaccozilla.kmp.compose.pageloaded`) only once everything it needs has arrived — its data *and* any content it loads, such as a page's Markdown file — so a test calls `waitUntilPageLoaded("<page-id>")` once and then makes plain assertions. Don't add `waitUntilAssertionPasses { ... }`, `Thread.sleep`/`delay`, or a per-element wait to paper over a load that isn't covered by the marker; make the screen emit `PageLoaded` later (once that load is done) so the marker covers it. A screen that starts loading something new must fold it into its `PageLoaded` condition in the same change. Use `assertPageNotShown("<page-id>")` to assert a page isn't showing.
- Click nodes that can appear freshly composed (menu items, autocomplete options, lazily laid out items) with `performClickWhenLaidOut`, which invokes the click semantics action directly instead of a coordinate-based gesture that can miss an ancestor-clipped node.
- Before writing the same non-trivial wait/assertion/interaction pattern at more than one call site, add a shared helper (in `compose-test-utils` if it is generic, otherwise in the project's own test-utils file) instead of copy-pasting it, and put the reasoning behind the pattern in the helper's comment once. If you're about to touch the second or third copy of a pattern written inline, extract it as part of that change.
